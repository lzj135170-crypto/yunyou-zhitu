# 检索策略：测出来的结论和取舍

这份文档记录**每一个检索策略开关开/关的实测差别、最终选的值、以及为什么**。

存在的理由很直接：调好的参数如果不写下来，下一次改动就会把它们冲掉，而且没人知道
原来为什么是这个值。所以这份文档里"没选"的选项、"被推翻的假设"和"尺子测不到的东西"
都跟结论一样重要。

**改任何和检索相关的东西之后，重跑一次 `scripts/eval_quality.py`，指标掉了就是回归。**

---

## 一句话结论

| 旋钮 | 现在的值 | 一句话理由 |
| --- | --- | --- |
| `rerank`（交叉编码器精排） | **开** | 唯一的决定性组件。关掉 nDCG 掉 **0.1022** |
| `rrf_k` | **60** | 10 / 60 / 100 给出**一位不差**的指标。别再动它 |
| `max_per_doc`（跨文档去重） | **关（0）** | 掉 recall。**负收益**，见下文 |
| `expand_parent`（父章节扩展） | **关** | 性价比被 `TOP_K=8` 全面比下去，见下文 |
| `weight_vec` / `weight_bm25` | **1.0 / 1.0（等权）** | BM25 收益很小（76 条里 1 条）但**落在 `hit@8 = 1.0000` 这个位置上**，见下文 |
| `TOP_K`（一次取几条） | **8**（原为 5） | `hit@8 = 1.0000`——取 5 时有 1 条用例彻底落空 |
| `EMBEDDING_DTYPE`（嵌入精度） | **不做** | 它要解决的问题目前不存在，理由见文末 |

⚠️ **这些开关刻意不放进 `app/config.py`。** 那个文件收的是"部署时按环境改的东西"
（连接串、端口、模型路径、密钥），而这一组是**代码级的设计决定**——值由本文档的
实测数据定下来，改它们该是一次带评估的提交，不是运维改个环境变量。

放进 config 的后果可以预见：某台机器上有人为了"试试看"设上 `MAX_PER_DOC=2`，
而那个值实测掉 0.0488 的 recall，且**没有任何报错**——线上质量悄悄变差，
代码库里查不到任何改动痕迹。

**要调它们，走评估脚本**（`--sweep` 看代价、`--self-check` 确认尺子没坏）。

## ⚠️ 本文档最重要的一条：检索指标全绿，但四分之一的问题根本没走检索

这条**不是**检索策略问题，是**接线问题**，而且 `eval_quality.py` **在结构上就看不见它**。

### 现象

端到端评估（`scripts/eval_answer.py`）跑前 10 条，其中 4 条的「资料长度」是 **0 字**：

```
[5] 成都住哪个区域比较方便   资料 0 字
[6] 成都住宿大概什么价位     资料 0 字
[7] 从成都怎么去都江堰       资料 0 字
[8] 成都有几个机场           资料 0 字
```

而同样这 4 条问题，`eval_quality.py` 测出来 **`hit@8 = 1.0000`** ——
`chengdu-hotels.md`、`chengdu-transport.md` 里就写着答案。**检索层完全够用，是图不叫它。**

裁判给这 4 条的判分是 依据 1/5、出处 1/5、完整 1/5，并逐条列出编造的事实：

```
春熙路房价 400–800 元/晚          ← 库里写着别的数
地铁2号线到犀浦站换乘城际列车      ← 库里写着交通方案
双流国际机场代码 CTU              ← 资料为空时一切具体事实都判无依据
```

### 根因

`rag` 被设计成**五个专家里的一个**（`EXPERT_NODES`），而 `hotel` / `transport` /
`attraction` 三个域专家**手里没有知识库**——它们给模型的指令是一句写死的话：

```python
# hotel.py 原来的样子
INSTRUCTION = "请根据上面的对话，推荐合适的住宿。"
```

于是 planner 看到"住宿"两个字就把任务派给 `hotel`，`hotel` 只能凭模型记忆回答。

**实测暴露面**（直接调 `_plan_with_llm`，76 条可答用例）：

| | 条数 |
| --- | --- |
| planner 调用 `rag` | 57 |
| planner **不调用** `rag` | **19（25%）** |

而且这 19 条**不是随机的**，全部集中在三类，恰恰是知识库覆盖得最好的三类：

| planner 的选择 | 典型用例 |
| --- | --- |
| `['hotel']` | 成都住哪个区域比较方便、成都住宿大概什么价位、三亚住哪个湾好、那住宿呢 |
| `['transport']` | 从成都怎么去都江堰、成都有几个机场、云南路线怎么走 |
| `['attraction']` | 哪些小众景点、青城山前山门票多少 |

⚠️ **`rag` 会不会被调用还取决于 LLM 掷骰子**：同一条「成都住哪个区域比较方便」，
两次跑分别得到 `['rag','hotel']` 和 `['hotel']`。所以这不是"某些问题路由错了"，
是**知识库会不会被查是不确定的**。

### 修法：检索从「一个专家」变成「所有专家的地面」

两处改动：

1. **`planner._retrieval_first()`** —— 把 `rag` 固定排在任务清单**第一位**。
   `_pick_next_task` 是按顺序取第一个未完成的，所以**排在后面等于没加**：
   `hotel` 会先跑，那时 `findings["rag"]` 还不存在。

2. **`_common._grounding()`** —— `run_expert` 把检索结果注入每个专家的指令。
   关键是**三种情况分开说**，不能都留空：

   | 情况 | 注入内容 |
   | --- | --- |
   | 检索到了资料 | 附上资料 + "所有具体事实都必须来自这里" |
   | 检索到但是空的 | "**没有检索到任何资料**，不要给任何具体数字" |
   | 检索失败 | 同上（失败更不能靠记忆补） |

   **中间那一行是这次修复的核心。** 原来的缺陷不只是"没有资料"，而是
   "没有资料**且模型不知道**"——它不知道自己手上没依据，照常给出具体数字。
   **模型不知道自己在编，是最难发现的一种错误：回答读起来完全正常。**

   ⚠️ `itinerary` 传 `ground=False`：它的指令里已经用 `_render_findings()`
   把全部 findings（含 rag 的 context）渲染进去了，再注入一次就是同一份
   两千字资料出现两遍。

### 修完的效果（同一批 10 条用例，端到端裁判，跑了三轮）

| | 依据性 | 出处 | 完整性 | 编造 |
| --- | --- | --- | --- | --- |
| **A. 修复前** | 2.90 | 1.90 | 3.10 | 6 / 10 |
| **B. 只做「检索前置」** | 4.60 | 2.30 | 4.70 | 2 / 10 ⚠️ |
| **C. 再加出处提示词 + 裁判补天气材料** | **5.00** | **4.90** | **5.00** | **0 / 10** |

⚠️ B 那 2 条"编造"**是假的**——它们是天气数据，裁判看不到，详见下一节。
也就是说 B 的真实编造率已经是 0。

四条零检索的用例逐条翻身（格式：依据/出处/完整）：

| 用例 | A | B | C |
| --- | --- | --- | --- |
| 成都住哪个区域比较方便 | 1/1/1 | **5/2/5** | 5/5/5 |
| 成都住宿大概什么价位 | 1/1/1 | **5/2/5** | 5/5/5 |
| 从成都怎么去都江堰 | 1/1/1 | **5/2/5** | 5/5/5 |
| 成都有几个机场 | 1/1/1 | **5/2/4** | 5/5/5 |

#### ⚠️ 这些数字能当结论的边界

**能当结论的**：四条零检索用例从"完全无依据"变成"关键事实全部有依据"。
这个变化的**结构性证据是确定的**——检索到的上下文字数从 **0 字**变成
**1689 / 1696 / 1982 / 2498 字**（对应上面四条用例），
这一项不受 LLM 抖动影响。修复前后走的是完全不同的代码路径。

**不能当结论的**：A→C 之间那 +2.10 的精确效应量。三次跑都是**同一批 10 条**，
但图里每轮有两次以上 LLM 调用（各专家 + 裁判），本身带抖动。

**必须警惕的一件事**：C 那一轮 **10 条全是满分**，也就是说
**这份 10 条的样本已经到顶、失去区分度了**——和 `hit@8 = 1.0000` 是同一个问题。
下次要量改进，得换更大的样本（`--limit 0` 跑全量），
或者这份评估只能用来"发现退步"而不是"衡量进步"。

**为什么确认这是真改进而不是裁判被改松了：**
① C 里第 2 条出处给了 4 分不是 5 分，说明裁判仍在区分；
② 裁判的理由逐条列出具体事实和它出自哪份材料的哪一节；
③ 答案里出现了真实的资料名和章节名（"以上信息出自《成都交通指南》的
「两个机场，别搞混」一节"）——这是提示词改动的**实际行为变化**，不是打分口径变化。

### 顺带修的两处

1. **`RESPONSE_PROMPT` 补上「出处」要求。**
   裁判测出来 `出处` 一直是最弱的一维（A 轮 1.90/5），而 `citations` 是
   **算好了、存进 findings、传到 response 手里的**——只是提示词里一次都没提出处。
   **信号一直在，没人要求用它。** 补上之后出口从 1.90 跳到 4.90。

2. **裁判自己的盲点：看不到实时天气数据。** 见下一节。

### 裁判自己出错了一次：把实时天气判成"编造"

修复后的那次跑，剩下 2 条"有编造"的用例是：

```
[9]  成都三天怎么安排     编造：10月16日至18日成都三天全是毛毛雨
[10] 成都什么时候去最合适  编造：16日降水概率92%、气温17.2—23.5℃
```

**这两条不是编的。** 它们是 `weather` 节点当次从 Open-Meteo 取的实时数据。
但裁判的输入只有 `rag.context`——**知识库里当然没有实时预报**，
于是它把"我看不到"当成了"你编的"。

⚠️ **这不是裁判的错，是喂给它的东西不全。** 而且危害很具体：

- 任何含天气的回答都会被**系统性扣分**，`依据性` 被压低
- 更糟的是**会误导出错误结论**——"模型在编天气"这个判断如果被采信，
  去改的就是提示词或模型，而真正的问题是评估脚本少传了一段材料

**修法**：`_judge()` 现在把两段原始材料都给裁判——知识库资料 + 天气接口数据，
后者单独标出「实时天气数据（不是知识库）」。

⚠️ **但只给"原始材料"，不给各专家节点的产出。** 这个区分是刻意的：
专家产出本身可能就是编的（这正是这次要查的东西），
拿它当依据等于**让被审查的人自己出证据**。所以给裁判的是接口返回的原始数据，
不是它写给用户的措辞。

**这条是「裁判必须人工抽查」这个要求实际抓到的。** 计划里写"一个不可靠的裁判
比没有裁判更糟——它给出一个看起来客观的数字，所有人都会引用它，而它是错的"，
这次就撞上了：如果没人去看那 10 条明细，`依据性 4.60` 里混着一个系统性偏差
永远不会被发现。

### 代价（有意接受的）

**1. 现在每一轮都会跑一次检索**，包括"明天天气怎么样"这种不需要知识库的问题。
多出来的是**一次 Query 改写（一次 LLM 调用，约 2—4 秒）加一次精排**。

**2. 那份资料会注入给每一个跑起来的域专家，不是只注入一次。**
注入的是 `attraction` / `hotel` / `transport` 三个（`rag` 是资料的产地，
`weather` 走自己的 HTTP 路径，`itinerary` 显式关掉），实测一轮通常跑 1—3 个。
`TOP_K=8` 时上下文约 1900 字 ≈ 1500 token，所以**每轮多出约 1500—4500 token 的输入**。

两条都接受，理由：**RAG 图里最贵的失败不是慢，是该查的时候没查。**

⚠️ 但第 2 条意味着 `TOP_K` 这个旋钮的**真实代价比检索指标显示的高**：
`eval_quality` 里 5→8 的代价是"+694 字上下文"，而实际影响是
"× 专家数"。改 `TOP_K` 时要把这个乘数算进去——它不影响结论方向
（命中率确实变好了），但影响取舍的边界。

### 怎么防止它再发生

这个缺陷给"两把尺子"的必要性提供了最强的一条证据：

> **检索指标（`eval_quality.py`）直接调 `pipeline.search()`，压根不经过 planner。
> 所以它能证明"检索器是好的"，但永远不能证明"检索器被用上了"。**

只有端到端那把尺子（`eval_answer.py`）能看见两者之间的那段缝。
**改任何和"什么时候检索"有关的东西之后，必须跑端到端评估，不能只看检索指标。**

## 怎么读这些数字

### 尺子本身

**语料**：`knowledge/` 下 18 篇 Markdown，**130 个块**，平均 7.2 块/篇，最多 12 块/篇。

**标注集**：`eval/qa_set.jsonl`，**86 条**，全部人工标注到 **`文件 + 章节`** 一级
（不标 `document_id`——那是自增的，删库重灌就全变了）。

| 类型 | 条数 | 考什么 |
| --- | --- | --- |
| `semantic` | 28 | 向量路（问法和原文没有字面交集） |
| `keyword` | 26 | BM25（专有名词精确匹配） |
| `exclusive` | 12 | 相似文档互斥（成都住宿 vs 三亚住宿） |
| `multiturn` | 6 | Query 改写的指代消解 |
| `multihop` | 4 | 需跨文档综合 |
| `unanswerable` | 10 | **正确地查不到**（知识库只覆盖 6 个目的地，问上海就该返回空） |

有期望答案的 76 条里，70 条期望 1 项、6 条期望 2 项（**且这 6 条的两项全在同一篇文档里**，
这个事实在下文判断去重策略时用得到）。

**指标**：`recall@k` / `hit@k` / `MRR` / `nDCG@k`。其中 **nDCG 是主指标**，因为精排的
全部意义就是改顺序。

⚠️ **`k` 跟着被测量的东西走**：策略对比那张表（第 1—5 节）都是在 `top_k=5` 下测的，
因为改那些旋钮时生产值还是 5；`top_k` 那张表（第 6 节）用的是**各自的 k**。
比指标之前先确认两边 k 一样——`recall@8` 和 `recall@5` 放一起比是没有意义的。

**生产配置在本文档写作过程中从 `top_k=5` 改成了 8**（理由见第 6 节），所以
`eval/baseline.json` 存的是 **`top_k=8`** 的那一版。

### ⚠️ 只有 `--no-rewrite` 是可复现的

Query 改写是一次 LLM 调用，抽出的过滤条件**每次都可能不同**。同一份代码、同一份语料，
连跑三次同一行：

| 当前默认（带改写）·第 N 次 | recall@5 | hit@5 | MRR | nDCG@5 |
| --- | --- | --- | --- | --- |
| 第 1 次 | 0.9756 | 0.9868 | 0.9215 | 0.9370 |
| 第 2 次 | 0.9756 | 0.9868 | **0.9007** | **0.9216** |
| 第 3 次 | 0.9756 | 0.9868 | **0.9226** | **0.9379** |

recall 和 hit 三次相同是运气，**MRR 和 nDCG 抖动幅度达 0.02**——比"关掉精排"之外
任何一项策略差异都大。

**所以基线只能用 `--no-rewrite` 存**（`--save-baseline` 会拒绝非确定性的基线，不是洁癖：
拿一个抖动的数当基准，下次跑出来的"退步"很可能只是抖动，而那种假警报会让人逐渐
忽略这个机制，等真退步时就没人在看）。所有策略对比同样都在 `--no-rewrite` 下跑，
否则分不清差异是开关造成的还是改写抖动造成的。

### ✅ 确定性已验证（两次独立全量跑，逐位相同）

`--no-rewrite` 模式下，把整套 sweep 完整跑了两遍（15 个配置 × 86 条 = 1290 次检索），
**每一个配置的四项指标都完全一致**：

```
关掉精排          0.8659 / 0.8947 / 0.7564 / 0.7877
只用向量路         0.9634 / 0.9868 / 0.8623 / 0.8899
只用关键词路        0.9390 / 0.9605 / 0.8535 / 0.8773
每篇最多 1 块      0.8293 / 0.8947 / 0.8311 / 0.8291
每篇最多 2 块      0.9146 / 0.9474 / 0.8509 / 0.8681
父章节扩展         0.9634 / 0.9868 / 0.8557 / 0.8869
父章节扩展+每篇1    0.8293 / 0.8947 / 0.8246 / 0.8261
rrf_k=10 / 100   0.9634 / 0.9868 / 0.8623 / 0.8899
```

**零差异。** 说明检索链路上没有没控住的随机源（`set` 迭代顺序、GPU 浮点不确定性、
重排的批处理边界都排除掉了）。这条比任何单个指标都重要——**指标不可复现的话，
上面所有对比都没法解释**。

### ⚠️ 不可答用例不进主指标

`recall@k` / `hit@k` / `MRR` / `nDCG@k` 四个函数**全部跳过没有期望的用例**——分母是空的，
算不了。这是个刻意的设计，但**不等于它们没被测**：它们由 `score_separation()` 单独衡量
（分数分布 + 各档拒答阈值的收益/代价表）。

⚠️ 代价是：**下面所有对比表都只反映 76 条可答用例**。一个把 10 条不可答用例全都
"答上来"的改动，在这几张表里**看不出来**。要单独跑主报告看分数分离度。

## 基线

```
.venv/Scripts/python.exe scripts/eval_quality.py --no-rewrite
```

| 配置 | recall@5 | hit@5 | MRR | nDCG@5 |
| --- | --- | --- | --- | --- |
| 当前默认（带改写，**不可复现**，见上文三次抖动） | 0.9756 | 0.9868 | 0.90~0.92 | 0.92~0.94 |
| **不带改写（可复现，策略行的基准）** | **0.9634** | **0.9868** | **0.8623** | **0.8899** |

**改写本身值多少**：nDCG **+0.032 ~ +0.048**（0.8899 → 0.9216~0.9379）。
这个区间不是误差，是改写本身的抖动范围（见上文三次跑的数据）。

即便取下限，**改写也是这份文档里第二大的单项收益**（仅次于精排的 +0.1022），
而且它是这笔账里最干净的一笔——同一个语料、同一套用例，唯一变量是有没有做
指代消解和同义词扩展。

⚠️ 顺带说明为什么"改写值多少"这件事**只能给区间不能给点值**：改写要调 LLM，
而 LLM 抽出的过滤条件每次可能不同。**能用点值表达的都是确定性模式下的对比。**

### 存下来的基线文件：`eval/baseline.json`（`top_k=8`）

```bash
# 存
.venv/Scripts/python.exe scripts/eval_quality.py --no-rewrite --top-k 8 --save-baseline eval/baseline.json
# 比（有回归会报警）
.venv/Scripts/python.exe scripts/eval_quality.py --no-rewrite --top-k 8 --baseline eval/baseline.json
```

⚠️ **`--top-k` 两边必须一致**，否则是拿 `recall@8` 比 `recall@5`。

**按类型拆开（`hit` / `nDCG`）：**

| 类型 | 条数 | hit | nDCG |
| --- | --- | --- | --- |
| `multihop` | 4 | 1.0000 | 1.0000 |
| `semantic` | 28 | 1.0000 | 0.9205 |
| `keyword` | 26 | 1.0000 | 0.9098 |
| `exclusive` | 12 | 1.0000 | 0.9072 |
| **`multiturn`** | **6** | 1.0000 | **0.6204** ← |
| `unanswerable` | 10 | — | — |

### ⚠️ `multiturn` 那个 0.6204 不是缺陷，是这把基线的构造性限制

**别拿这个数去"优化多轮检索"。** 基线跑在 `--no-rewrite` 下，而"那住宿呢"这类问题
**必须靠改写补全主语**才能检索对——关掉改写之后它注定答不准。
所以多轮那一档是被**构造性地削弱**的，量到的不是真实表现。

**这暴露了一个取舍**：
- 回归基线**必须**是确定性的 → 只能 `--no-rewrite`
- 而 `--no-rewrite` 下**多轮场景天生测不准**

**结论：这份基线对单轮查询是可信的回归守门员，对多轮不是。** 多轮的质量只能靠
带改写的运行（或 `eval_answer.py` 的端到端裁判）来看，而那两个都不可复现，
只能看趋势、不能做门禁。

### 拒答阈值：数据支持，但还没做

`score_separation()` 输出的分数分布（`top_k=8`，76 可答 / 10 不可答）：

| | top-1 中位分 |
| --- | --- |
| 可答查询 | 0.9870 |
| 不可答查询 | **0.0504** |

中位数差 19 倍，但**尾部是重叠的**。看阈值表里最划算的一档：

| 阈值 | 拒掉不可答（收益） | 误伤可答（代价） |
| --- | --- | --- |
| **0.111** | **6 / 10** | **0 / 76** |
| 0.135 | 7 / 10 | 1 / 76 |
| 0.161 | 8 / 10 | 2 / 76 |
| 0.449 | 10 / 10 | 5 / 76 |

**阈值取 0.111 能白捡 60% 的拒答率、零代价。** 但**现在没有实现**——评分是精排
模型的原始分，量纲和这个实验不完全一样，真要上得先在同一条路径上重新标定。

⚠️ 而且代价那一边**更值钱**：把能答的问题判成"查不到"，用户会觉得功能坏了；
把答不了的硬答一句，用户至少能从内容看出不对。**阈值应该往低取。**

## 逐项结论

### 1. `rerank` —— 唯一的决定性组件

| 配置 | `top_k=5` · recall/hit/MRR/nDCG | ΔnDCG | **`top_k=8`（生产）· 同上** | ΔnDCG |
| --- | --- | --- | --- | --- |
| 基准 | 0.9634 / 0.9868 / 0.8623 / 0.8899 | — | 0.9878 / 1.0000 / 0.8642 / 0.8952 | — |
| **关掉精排** | 0.8659 / 0.8947 / 0.7564 / **0.7877** | **−0.1022** | 0.9268 / 0.9605 / 0.7661 / **0.8083** | **−0.0869** |

**选：开。** 两个 `k` 上都是最大的单项差异。

⚠️ 但在 `top_k=8` 上它的领先**缩小了**：`top_k=5` 时它比第二大的
（去重 −0.0608）大一倍，`top_k=8` 时（−0.0869 vs −0.0661）只领先一点。
原因和 `k` 变大是同一件事——**名额一多，候选生成的质量就没那么要命了**，
排序的重要性相对下降。这不改变结论（仍然该开），但说明**"精排值多少"
这个数随 `top_k` 变**，引用它的时候要带上 `k`。

代价是 1.13 GB 显存 + 每次检索一次交叉编码器推理。值。

**推论**：既然最终顺序完全由精排决定，那**融合层（RRF）的排序质量就不重要**——
它只需要把好的候选送进精排的候选池。这解释了下面第 5 节里 BM25 为什么"没用"。

### 2. `rrf_k` —— 完全不敏感，别再动它

| 配置 | recall@5 | hit@5 | MRR | nDCG@5 |
| --- | --- | --- | --- | --- |
| `rrf_k=10` | 0.9634 | 0.9868 | 0.8623 | 0.8899 |
| `rrf_k=60`（基准） | 0.9634 | 0.9868 | 0.8623 | 0.8899 |
| `rrf_k=100` | 0.9634 | 0.9868 | 0.8623 | 0.8899 |

**选：60（原论文默认值，等于不改）。**

三个值给出**逐位相同**的四项指标。`pipeline.py` 里那段注释——"这一层是候选生成器
不是排序器，k 取 10 还是 60 对用户看到的结果影响很小"——当初是推测，现在有数据了。

⚠️ **这一项不要再花时间。** 它不是"还没调到最优"，是**在当前架构下没有最优可调**。

### 3. `max_per_doc`（跨文档去重）—— 负收益

| 配置 | recall@5 | hit@5 | MRR | nDCG@5 | ΔnDCG |
| --- | --- | --- | --- | --- | --- |
| 基准 | 0.9634 | 0.9868 | 0.8623 | 0.8899 | — |
| 每篇最多 **2** 块 | 0.9146 | 0.9474 | 0.8509 | 0.8681 | −0.0218 |
| 每篇最多 **1** 块 | 0.8293 | 0.8947 | 0.8311 | 0.8291 | −0.0608 |

**选：关（不限）。**

#### 这一项差点被误判成"标注口径造成的假象"

`每篇最多 1 块` 那一行掉得很厉害时，第一反应是**尺子的问题**：如果一条用例期望的两个
章节本来就在同一篇文档里，限流之后必然丢掉一个——那是标注方式的代价，不是策略真的差。

查了标注集：86 条里确实有 6 条期望 2 项，**而且这 6 条的两项全部同文件**。所以这个
怀疑有依据。算一下它能解释多少：N=1 时那 6 条各最多拿 0.5，**recall** 最多掉
6 × 0.5 / 86 = **0.035**。

对不上。实测 recall 掉了 **0.1341**（0.9634 → 0.8293），口径只能解释其中 0.035。

**更干净的证据是 `每篇最多 2 块` 那一行：N=2 时两条期望都放得进来，口径损失为零，
recall 仍然掉了 0.0488。** 这是纯粹的答案丢失。

**结论：去重是真实的负收益，不是尺子的假象。** 它换来的是"上下文里文档更分散"，
代价是 5% 的时候正确答案被挤出去。这笔买卖不划算。

> #### 但要知道它的收益是什么、以及为什么尺子看不见
>
> 加这个开关的动机是 `pipeline.py` 里记的那个已实测缺陷：**单篇文档的多个块占满 top-k**
> （见过「成都 攻略」返回的 3 条全来自同一篇）。
>
> 这把尺子**衡量的是"对的章节有没有回来"，衡量不了"回来的东西是不是全来自同一篇"**。
> 所以这里只能说：**代价是量出来的 0.0488，收益是没量出来的**。收益大概率真实存在，
> 但它得靠 `eval_answer.py` 的裁判（`complete` 维度）或者一个专门的多样性指标来量，
> 不是靠重建召回率。
>
> **不能因为"收益没量出来"就说"没有收益"**——但也不能拿一个量不出来的收益去换一个
> 量得出来的 0.0488。所以现在是关的。

### 4. `expand_parent`（父章节扩展 / small-to-big）—— 有更好的替代方案

| 配置 | recall@5 | hit@5 | MRR | nDCG@5 | ΔnDCG |
| --- | --- | --- | --- | --- | --- |
| 基准 | 0.9634 | 0.9868 | 0.8623 | 0.8899 | — |
| 父章节扩展 | 0.9634 | **0.9868** | 0.8557 | 0.8869 | −0.0030 |
| 父章节扩展 + 每篇最多 1 | 0.8293 | 0.8947 | 0.8246 | 0.8261 | −0.0638 |

**选：关。**

**recall@5 和 hit@5 一模一样**——这是**符合设计**的：这个策略改变的是**返回内容**，
不是**哪些章节被返回**。所以章节级的指标天然看不见它。MRR/nDCG 那 −0.0030 是精排
看到更长的文本之后顺序略有扰动，量级很小。

它的真实收益是**上下文更厚**：单条命中实测从 536 字变成 722 字。加它的动机就是
原 `TOP_K = 5` 那段注释里写的"5 × 200 字 ≈ 1000 字，离上下文预算（3000 字）还有余量"
——**余量摆在那儿没用掉**。

⚠️ **所以这一项的正确判据不是召回率，是"上下文字数"和端到端答案质量。**

#### 对比：它和「提高 top_k」争同一份额度，而且输了

两种情况都在填那个没用掉的余量，做**正面比较**：

| 方案 | 字数 | hit@k | recall@k |
| --- | --- | --- | --- |
| `top_k=5` + 父章节扩展 | ~1630（1207 × 1.35） | 0.9868 | 0.9634 |
| **`top_k=8` + 不扩展** | **1901** | **1.0000** | **0.9878** |

**同样约 1900 字的预算，多取块在两项指标上都赢。**

原因说得通，而且是个可推广的判断：**父章节扩展加进来的是相关块「周围」的文字**
（那个章节里没被问到的部分），**而多取块加进来的是「另一条」相关内容**。
前者是稀释，后者是增量。

所以 `expand_parent` 的结论从"中性偏负、收益测不到"变成更明确的
**"有更好的替代方案"**。要填上下文预算，先调 `top_k`。

### 5. `weight_vec` / `weight_bm25` —— 等权，BM25 留着（收益小，但落点很关键）

**这一节走过一段弯路，完整的记录下来**，因为弯路上的那个判断错误比结论本身更值钱。

#### 第一轮：`top_k=5` 上，`w_bm25=0` 和等权**逐位相同**

| 配置 | recall@5 | hit@5 | MRR | nDCG@5 | ΔnDCG |
| --- | --- | --- | --- | --- | --- |
| 基准（等权） | 0.9634 | 0.9868 | 0.8623 | 0.8899 | — |
| 只用向量路（`w_bm25=0`） | 0.9634 | 0.9868 | 0.8623 | **0.8899** | **0.0000** |
| 只用关键词路（`w_vec=0`） | 0.9390 | 0.9605 | 0.8535 | 0.8773 | −0.0126 |

**选：保持等权。BM25 留着。**

#### 这一行差点被当成 bug（`top_k=5`）

`w_bm25=0` 和等权给出**逐位相同**的四项指标。计划里当时写的是：

> `w_bm25=0` 的指标必须**明显差于**等权。如果没差，说明关键词路在裸奔，
> **那是要查的问题而不是要调参**。

于是专门写了个诊断（`scripts/diagnose_branches.py`）绕过指标直接比较候选集合：

| | 不带改写（sweep 模式） | **带改写（生产配置）** |
| --- | --- | --- |
| `w_bm25=0` 与等权融合出**完全相同**的候选序列 | **0 / 76** | **0 / 76** |
| 融合后 top-30 里**只由 BM25 召回**的条数 | 平均 **5.3** 条 | 平均 **0.18** 条 |
| **BM25 一条独有都没贡献**的查询 | **0 / 76** | **70 / 76** |

**结论：不是 bug，也不是裸奔。**

1. **开关是接上的**：76/76 条查询的融合候选序列都不同，`_fuse` 确实收到了新权重。
2. **指标不动的原因不是"没差别"，是"差别不在集合上，只在顺序上"**——
   而最终 top-5 由精排决定（见第 1 节），精排会把 RRF 排的顺序**重新排一遍**。
   BM25 让候选重新排了序，净效果为零。

   ⚠️ **这个解释在 `top_k=5` 上成立，但它不是全部真相**——
   往下看"换到 `top_k=8`"那一节：名额一放开，BM25 那些独有候选就挤进来了。
   当时的推理少想了一步：**"落在 top-5 之外"和"永远没用"不是一回事。**

#### 一个反直觉的观察：**Query 改写越好，BM25 越没用**

生产配置（带改写）下，**76 条里 70 条 BM25 一条独有候选都贡献不出来**（平均 0.18 条）。
而*不带改写*时 BM25 平均贡献 5.3 条独有候选、且 0/76 条毫无贡献。

这个反直觉的结果有个干净的因果解释：**改写的关键词是模型给的同义词扩展过的词表**
（"住宿" → 住宿/酒店/民宿/客栈）。而**同义词扩展正是 BM25 相对向量路的唯一优势**——
BM25 是字面匹配，不做扩展就搜不到写成"酒店"的文档。改写把这件事提前做了，
BM25 就只剩"把向量路已经找到的东西再找一遍"。

**这个推论值得记住：如果哪天打算砍掉改写，BM25 的价值会同时回来。**

#### 保留它的理由

1. **候补池太小，测不出真假。** 130 个块，**每一路各召回 30 条 = 全语料的 23%**。
   两个方法各取四分之一语料，重合度必然极高——这是这份语料规模决定的，
   不是 BM25 这个方法的性质。**语料扩大 10 倍之后这个实验需要重做。**
2. **它是唯一不依赖模型的召回路径。** `_recall()` 里两条路各 try 各的：嵌入模型
   加载失败时只剩 BM25（`backend` 字段会如实报成 `bm25`）。砍掉它，非模型降级路径
   就只剩 `documents` 元数据表那个弱得多的关键词平替。
3. **它的开销很小**：一次 SQL，没有模型推理，没有显存。

⚠️ **但别在它上面继续投入**（比如调 BM25 的 k1/b 参数），除非先重做第 1 条
那个实验。它现在的作用是"不拖后腿，且在 `top_k` 放大时能补上最后一条用例"，
不是"混合检索提升了效果"。

#### ⚠️ 换到生产的 `top_k=8` 之后，BM25 **确实**产生了可测收益

上面整节的数字都是在 `top_k=5` 下测的，而生产值是 8。补测之后结论**变了**：

| 配置 | `top_k=5` · recall/hit/nDCG | **`top_k=8`（生产）· recall/hit/nDCG** |
| --- | --- | --- |
| 基准（等权） | 0.9634 / 0.9868 / 0.8899 | 0.9878 / **1.0000** / 0.8952 |
| **只用向量路（`w_bm25=0`）** | 0.9634 / 0.9868 / **0.8899** | 0.9756 / **0.9868** / **0.8926** |
| 差值 | **0.0000 / 0.0000 / 0.0000** | **−0.0122 / −0.0132 / −0.0026** |

**`top_k=5` 上"等权 = 纯向量"是逐位相同的；`top_k=8` 上不再相同。**

原因就是当初的推断：`_select` 从 30 条候选里取的名额从 5 个变成 8 个，
**多出来的三个名额让 BM25 那些独有候选有机会挤进最终结果**——
而且正好够把那条原本完全检索不到的用例捞回来（`hit@8` 从 0.9868 变成 1.0000）。

⚠️ **这个收益很小**：差距是 76 条里的 1 条。但它落在**最要紧的那个位置上**——
`hit` 从 0.9868 到 1.0000 意味着"**76 条可答问题里再没有一条完全检索不到**"，
而那正是第 6 节把 `TOP_K` 从 5 改成 8 的唯一理由。**BM25 是这个收益的一部分来源。**

⚠️ **教训比结论本身更值得记**：这一节原来标注的是"已知缺口，不是已验证的结论"，
而当时如果省掉那次补测、直接沿用 k=5 的结论写"BM25 不产生可测收益"，
那就是**把一条没测过的推断当成结论写进了文档**——而它恰好是错的。
换一个旋钮（这里是 `TOP_K`）之后，**所有在其他旋钮下测出来的结论都要重新确认。**

#### 顺带冒出来的一个新问题：`k=8` 上「改写」好像**降低**了召回

`top_k=8` 那一版 sweep 的两条基线（注意：带改写那行**不可复现**，只跑过一次）：

| 基线 | recall@8 | hit@8 | MRR | nDCG@8 |
| --- | --- | --- | --- | --- |
| 当前默认（**带改写**） | **0.9756** | **0.9868** | 0.9029 | **0.9232** |
| 不带改写 | **0.9878** | **1.0000** | 0.8642 | 0.8952 |

**改写把排序做好了（nDCG +0.0280），却把召回做差了（recall −0.0122、hit 掉一整条）。**

这和第 5 节 BM25 那一幕是同一个形状：**召回变差、排序变好**。最可能的原因是改写
会抽出 `city` 做硬过滤，而**过滤掉的那篇正好是某条用例的答案**：

- `k=5` 上没暴露，因为那时无改写的基线自己也够不到 1.0000
  （改写 0.9756 / 无改写 0.9634，改写反而更高）
- `k=8` 上无改写摸到了天花板（0.9878 / 1.0000），改写的召回短板才显出来

⚠️ **这是个待查的问题，不是结论。** 带改写那行跑一次变一次（MRR 抖动达 0.02，
见上文），所以"改写降低召回"这件事**需要多跑几次确认方向**，
再隔离出"是 `city` 过滤造成的还是改写本身的措辞造成的"——
`merge_filters` 里那段 `doc_type` 的教训（硬过滤把正确答案整篇排除）还热着。

**在查清楚之前，不要动 `city` 过滤**：它在 `k=5` 上是零代价的，
而这里看到的 0.0122 差异可能只是那一次改写的抖动。

### 6. `TOP_K`（一次取几条）—— **从 5 改成 8**

| top_k | recall@k | **hit@k** | MRR | nDCG@k | 平均上下文字数 |
| --- | --- | --- | --- | --- | --- |
| 3 | 0.9390 | 0.9737 | 0.8596 | 0.8813 | 739 |
| **5（原值）** | 0.9634 | 0.9868 | 0.8623 | 0.8899 | 1207 |
| **8（新值）** | 0.9878 | **1.0000** | 0.8642 | 0.8952 | **1901** |
| 12 | **1.0000** | 1.0000 | 0.8642 | 0.8976 | 2707 |

⚠️ 这张表的 recall 是**单调上升**的——名额变多就必然多召回，那本身不是"质量变好"。
要看的是**每多花一个字买到多少召回**。

#### 决定性的一行是 `hit@8 = 1.0000`

`hit@5 = 0.9868` 意味着 76 条可答用例里**恰好有 1 条完全检索不到任何相关内容**。
那不是"指标差一点"，那是**用户拿到一个没有任何资料支撑的回答**——而 RAG 的价值
全在于此。取 8 条时这个数字是满的。

#### 为什么不是 12（它 recall 满分）

边际收益腰斩：

| 跨度 | recall 增益 | 字数代价 |
| --- | --- | --- |
| 5 → 8 | **+0.0244** | +694 字 |
| 8 → 12 | +0.0122 | **+806 字** |

同样买到 0.0244 的召回，5→8 花 694 字，8→12 要花 1600 多字。而且 12 条会占到
上下文预算（3000 字）的 **90%**，把余量吃干——那样以后任何"再多放点资料"的尝试
都没有空间了。

#### 为什么不是 3（它更省）

`hit@3 = 0.9737` → 76 条里有 2 条彻底落空，recall 掉 0.0244，只省 468 字。
省下来的字没有花在别处，等于白省。

#### ⚠️ 一个后果：`hit@k` 在 k≥8 上饱和了

`hit@8` 和 `hit@12` 都是 1.0000，`recall@12` 也是满分。**这意味着这把尺子的召回维度
用到头了**——以后再提升检索，`hit` 和 `recall` 不可能再给出任何区分度，只能看 nDCG
和 `eval_answer.py`。想恢复区分度只有一条路：**扩大语料和标注集**。

### 7. `EMBEDDING_DTYPE`（嵌入精度 fp32 → fp16）—— 不做

**计划里本来要做**（它是唯一一个"既影响质量又影响显存"的维度：bge-m3 是 fp32 占
2.27 GB，reranker 用 fp16 只占 1.13 GB，两个模型精度不一致是当初顺手写的）。

**决定不做，理由：**

1. **它要解决的问题目前不存在。** 实测单进程加载两个模型是 3.39 GB，空闲显存 6.96 GB，
   **余量一倍多**。这个维度只在"要在一个进程里塞两套模型"时才有价值，而那个场景
   （MCP server 同时跑模型）已经定了**让 MCP server 跑 CPU**。
2. **换精度必须重灌全部 130 个向量**，而且**混着用会静默塌陷**——库里的向量和查询向量
   不在同一个尺度上时检索质量整体下降，**没有任何报错**。为一个不存在的问题付这个风险
   不划算。
3. **它是一次性实验，不是长期旋钮。** 真要做的话正确做法是"在临时表上测一次，
   决定用哪个值，然后把另一个删掉"，而不是在 `config.py` 里长期留一个能静默毁掉
   整个向量库的开关。

**什么时候重新考虑**：出现第二个需要同时持有模型的进程，或者模型换成更大的。

## 降级行为（实测，不是设计意图）


脚本会**真的停掉 `travel-pgvector` 容器**，跑完在 `finally` 里重启。

实测 13 项断言全过：

| 状态 | `backend` | `context` | 抛异常 |
| --- | --- | --- | --- |
| 正常 | `pgvector+bm25+rerank` | 非空（带【编号】） | — |

而不是让用户以为这是正常的检索结果。

## 被推翻/被澄清的假设

1. **"混合检索一定比单路好"** —— **在 `top_k=5` 上完全没被证实，在 `top_k=8` 上被证实了一点点。**
   `top_k=5` 时等权融合 = 纯向量，一位不差；`top_k=8`（生产值）时
   去掉 BM25 会让 `hit@8` 从 1.0000 掉到 0.9868 —— **差距是 76 条里的 1 条**。
   见第 5 节。不是"混合检索没用"，是**这份语料的候选池太大（每路召回全语料的 23%），
   两个方法区分不开**。

   ⚠️ 这一条同时是个**方法论教训**：同一份数据在 `top_k=5` 和 `top_k=8` 下
   给出相反的结论。**换任何一个旋钮之后，其他旋钮上测出来的结论都要重新确认。**

2. **"`doc_type` 可以当过滤条件"** —— **被推翻过，已经修了。**
   早期实现按 `city + doc_type` 硬过滤，nDCG **掉到 0.7432**，比不做改写
   （0.8899）还差一大截；同一套代码去掉 `doc_type` 之后回到 0.9370。
   根因不是模型抽错了，是**元数据的粒度错了**：
   `doc_type` 标的是"这份文档是什么体裁"（攻略/景点/美食），而用户问的是
   "我想找什么内容"。攻略类文档天然包含住宿/美食/交通各小节，硬过滤会把正确答案
   整篇排除。现在只按 `city` 过滤。完整记录见 `app/rag/rewrite.py` 的 `merge_filters`。

3. **"加了开关就能解释差异"** —— 至少这一次不是。`w_bm25=0` 那一行是**指标完全
   看不见的行为差异**（候选集合 76/76 都变了，指标一动都不动）。
   **指标没动不等于没变化**——这一条值得记住。

4. **"上下文不够厚，就该把块撑大"** —— **被推翻，正确做法是多取块。**
   加 `expand_parent` 的动机是"5 条 × 200 字 ≈ 1000 字，预算 3000 字没用完"。
   但同样约 1900 字的预算下，`top_k=8`（hit 1.0000 / recall 0.9878）
   **全面好过** `top_k=5` + 父章节扩展（约 1630 字，hit 0.9868 / recall 0.9634）。
   多取块加进来的是**另一条**相关内容，撑大块加进来的是**这一条周围**没被问到的内容。
   见第 4 节和第 6 节。

5. **"`hit` 和 `recall` 越高说明检索越好"** —— **到 k=8 为止是这样，之后失效。**
   `hit@8` 和 `hit@12` 都是 1.0000。**换句话说：从这个版本开始，
   这两个指标不可能再变好了。** 下次有人说"我优化了检索，hit 到 1.0 了"，
   要看的是他有没有扩语料——没扩的话那个 1.0 早就是了。

## 这把尺子的已知盲区

改之前先看这一节，有些问题它答不了，别拿它当全能裁判。

| 盲区 | 后果 | 用什么代替 |
| --- | --- | --- |
| **完全看不见 planner 的路由** ⚠️ | 检索指标能证明"检索器是好的"，**永远不能证明"检索器被用上了"**。曾经 25% 的问题根本没走检索，而这张表全绿 | **`eval_answer.py`**（只有它能看见那段缝） |
| **`hit` / `recall` 在 k≥8 上已饱和** | 指标已经满分，**再提升检索它们给不出任何区分度** | 看 nDCG 和 `eval_answer.py`；想恢复区分度只能扩语料+扩标注集 |
| **多轮场景在基线里被构造性削弱** | `--no-rewrite` 下"那住宿呢"注定答不准，`multiturn` 的 nDCG 0.6204 不代表真实水平 | 带改写的运行看趋势（不可复现，不能做门禁） |
| **看不见文档多样性** | `max_per_doc` 的收益（不让单篇占满）量不出来 | `eval_answer.py`，或专门写一个多样性指标 |
| **看不见 10 条不可答用例** | 所有对比表只管 76 条可答用例 | 主报告的 `score_separation()` |
| **候选池 = 全语料的 23%** | 两路召回的差异被淹没。"BM25 有没有用"这类问题**在 `top_k=5` 上答不准**（实测两个配置逐位相同），换到 `top_k=8` 才测出 76 条里 1 条的差 | 语料扩大后重做；在此之前别用这份数据判断某个召回分支该不该留 |
| **结论依赖其他的旋钮** | 第 5 节在 `top_k=5` 上说"BM25 无收益"，在 `top_k=8` 上说"有收益"。**同一份数据、同一套用例，只因为另一个旋钮不同** | 改任何一个旋钮后，重跑 `--sweep --top-k <生产值>`，别沿用旧结论 |
| **不会因"上下文变长"扣分** | 一个字也不放进答案的配置，`recall`/`nDCG` 反而可能更高 | `context_chars` 列（就是为它加的） |
| **造语料的和出题的是同一个人** | 出题时不知不觉会偏向语料里写过的说法 | 换人出题，或者用真实用户问句 |

## 待查：`w_bm25=0` 的召回下降，和我能解释的机制对不上

**2026-10-17，加完分支级归因之后发现的，暂时没有根因。**

分支归因第一次跑出来的数（`--no-rewrite --top-k 8`）：

```
候选生成层的上限（两路并集，不看排第几）        1.0000
融合+精排之后的最终 recall@8                    0.9878
├ 并集里就没有 → 问题在【召回】                 0.0000
└ 并集里有但没进 top-8 → 问题在【排序】          0.0122

分支      top-5    top-10    top-30
bm25     0.7561    0.8415    0.9512
vec      0.9268    0.9756    1.0000      ← 向量路【自己】就到顶了
```

### 矛盾在哪

`vec` 的 top-30 单独就覆盖 **100%** 的期望项。而 `_fuse` 里 `w_bm25=0` 时，
BM25 独有的候选 rrf 是 0、必然排在所有向量候选之后，所以
`merged[:30]` 应该是向量路 top-30 的**超集**。

**候选池是超集 → 精排看到的东西不少于原来 → 最终 recall 不该掉。**

但实测 `w_bm25=0` 的 `recall@8` 是 0.9756，比基线的 0.9878 低 0.0122。

我直接量了候选池：**76 条用例的候选序列全都不同**，而纯向量路的池子
**长度从不更小**。所以差异确实不在池子的内容多少上。

### 已排除的

- 不是"池子里没有答案"——`oracle_recall` 和 `vec@30` 都是 1.0000
- 不是 `cand_total` 不同——两条路走的都是同一个 `total`
- `CrossEncoder.rank()` 是逐对打分，**理论上与输入顺序无关**

### 还没排除的

精排的**批处理/浮点**对输入顺序敏感（30 条候选、`BATCH_SIZE=32` 是一个批次，
但 padding 和排序里的并列处理都可能引入顺序相关的结果）。

### ⚠️ 为什么先记下来不继续查

上面那两个 1.0000 **不受这个谜题影响**——它们来自 `_recall` 的原始输出，
不经过融合和精排。受影响的只有"`w_bm25=0` 到底掉了什么"这一件事，
它只关系到 Phase 3 要不要留 BM25。

**但在查清楚之前，不能用"BM25 的独有贡献"来解释任何东西**——
那句话现在建立在一个我没能解释的现象上。

## 分支级归因：召回层零损失，全部损失在排序

**2026-10-17 加，`eval_quality.py --branches`。**

在这之前，"BM25 到底有没有用"要靠一次性脚本 `diagnose_branches.py` 去跑、
再人工比对候选集——**可解释性靠考古**。现在它是常规出口。

```
候选生成层的上限（两路并集，不看排第几）        1.0000
融合+精排之后的最终 recall@8                    0.9878
├ 并集里就没有 → 问题在【召回】                 0.0000
└ 并集里有但没进 top-8 → 问题在【排序】          0.0122

分支      top-5    top-10    top-30
bm25     0.7561    0.8415    0.9512
vec      0.9268    0.9756    1.0000
```

### ⚠️ 这推翻了"尺子饱和所以不能改召回"的说法

`oracle_recall = 1.0000` —— **两路并集覆盖了每一个期望项，召回层一点没漏。**
最终那 0.0122 的缺口**全部是排序问题**（在池子里，但没排进前 8）。

**所以"更准"的空间在排序，不在召回。** 对应的指标是：

```
nDCG@8 = 0.8952   ← 还有 10% 空间
MRR    = 0.8642   ← 还有 14% 空间
```

计划里原本写的"加难题让召回维度恢复分辨力"**方向不对**：
召回已经是满分，加更难的题只会让它掉下来，而**掉下来的那部分仍然要靠
MRR/nDCG 才能定位到"是召回掉的还是排序掉的"**。
`--branches` 那一节就是干这个的——它把两者分开了。

### 向量路单独就到顶了

`vec` 的 top-30 命中率 **1.0000**，而 `bm25` 只有 0.9512。
**向量路自己就能找回全部正确答案。**

⚠️ 但这**不能**直接推出"BM25 该删"——见下面那条待查事项：
`w_bm25=0` 实测会让最终 recall 掉 0.0122，而按候选池的包含关系它不该掉。
**在解释清楚那件事之前，不能拿这个数当砍 BM25 的依据。**

## 难题集 `qa_hard.jsonl`：测出来的东西和设计它的目的不是一回事

**2026-10-17 加，`eval_quality.py --qa`。**

18 条用例，出题思路是"期望的章节和它的邻居在结构上高度相似，逼排序做区分"：

```

```

### ⚠️ 先说没成立的：设计时的断言被推翻了

计划里给这一项写的验收标准是 **`hit@8 < 1.0000`——"仍是 1.0 说明题不够难，重出"**。
实测就是 1.0。**这条断言是错的，而且错得可以证明：**

> 我把 `qa_hard.jsonl` 第一条的 gold 标签改成一个故意对不上的章节，
> `hit@8` 立刻从 **1.0000 掉到 0.9167**。**题目一个字没变难。**

所以 `hit@8` 在这个配置下**不是一个难度旋钮**——它只回答
"期望的那一块在不在候选池里"，而候选池是**全语料 130 块的 23%**
（`CAND_FRACTION=0.23`）融合出来的。池子这么大，只要题是语料**答得出**的，
gold 基本不可能掉出去。`oracle_recall = 1.0000`（上一节）说的也是这件事。

**想把 `hit@8` 压到 1.0 以下，唯一的办法是出语料答不了的题**——
而那测的是"gold 存不存在"，不是"检索难不难"。**所以没有去重出题。**

### 真实分布：16/18 排第 1，2/18 排第 2、3

```
r=3  锦里的小吃怎么样        gold=('锦里古街',)
       1. chengdu-food.md      :: ('先记住一句话',)
       2. chengdu-food.md      :: ('小吃街对比',)
       3. chengdu-attractions.md :: ('锦里古街',)   <= 正确答案

r=2  西安洒金桥吃饭人均多少    gold=('街区对比',)
       1. xian-food.md :: ('预算参考',)
       2. xian-food.md :: ('街区对比',)             <= 正确答案
       3. xian-food.md :: ('招牌美食与人均价格',)
```

两条都**核过语料，gold 标得对**：

- 第 1 条：问"小吃"，字面命中美食文档的《小吃街对比》，
  但答案在景点文档的《锦里古街》里。**撞车发生在文档之间。**
- 第 2 条：《街区对比》里有"洒金桥（本地人首选）… 人均 20—30 元就能吃饱"，
  是正确答案；赢它的《预算参考》里是"学生党人均 30 元/天"——**那是全天预算，
  不是洒金桥的人均**。两处都有"人均"，字面分不开。
  （《招牌美食与人均价格》提到"洒金桥 129 号"，但那是个**地址**，不是人均。）

### 所以它是什么：**表面词撞车集**，不是"更难的集"

这 18 条真正在测的是一件事：**问句里的表面词恰好和错误的兄弟章节撞车时，
排序能不能靠语义把它掰回来。** 16/18 能，2/18 不能。

⚠️ 它**不是**比 86 条那套更灵敏的排序尺子——它的 MRR 反而更高
（0.9352 vs 0.8642）。原因不是它更容易，是**它是单 gold 的**：
每条只有 1 个期望项，排第 1 就满分；而主用例集里多条用例有 2—3 个期望项，
**注定有 gold 落在第 2 名之后**。要测排序灵敏度，主用例集比它强。

**它的价值只在一条上**：那 2 条撞车用例是主用例集里没有的失败模式，
现在被 `eval/baseline_hard.json` 钉住了（指纹含 `cases_digest`，
改一条 gold 也会拒绝对比）。改精排 / 改融合时跑它，看这 2 条有没有被修好、
或者有没有从 16 条里再掉下来。

### 出题时该记下的教训

按"结构相似"出题（我原来的思路）**不产生难度**——邻居章节长得像，
向量和精排本来就能分开，照样排第 1。真正产生难度的是
**表面词撞车**：问句里的词出现在错误的章节里，而且出现得**很自然**。
以后加题按这个来。

顺带一条：出这种题时**必须核语料**。第 2 条如果我没去读原文，
会把它当成"检索错了"，而实际上 gold 差一点就标错——
《招牌美食与人均价格》看着比《街区对比》更配"人均多少"这个问法。

# Phase 2：契约收口——契约本身有个洞，而且接口的文档在教人往里跳

**2026-10-17。** 这一阶段的计划是"一个命中一种形状、失败词表统一、filters 加校验"。
做完之后**最大的收获不是那三件事，是第三件查出来的一个真 bug**。

## ⚠️ 先说 bug：`filters` 的文档在教调用方踩一个已经修过的坑

`RagSearchRequest.filters` 的说明原文写着：

> 元数据过滤，如 `{'city': '成都'}`。**受控字段是 city 和 doc_type。**

而 `rewrite.merge_filters` 里有一段很长的注释，用实测数据论证了
**doc_type 不能用来硬过滤**（掉 0.15 召回），并对模型抽出来的 doc_type 做了丢弃处理。

**两件事同时成立，因为校验只做了一半**：

```python
if extracted.city and extracted.city in CITIES:   # 模型抽的 → 有校验
    merged["city"] = extracted.city
...
if explicit:                                       # 调用方传的 → 一行校验都没有
    merged.update({k: v for k, v in explicit.items() if v})
```

于是**照着接口文档传 `doc_type` 的调用方，把那个 0.15 的损失原封不动请了回来**，
而且全程没有报错。实测（`rewrite` 关掉，排除模型抽取的干扰）：

| 查询 | 无过滤（正确） | `doc_type=景点` 修复前 | 修复后 |
|---|---|---|---|
| 北京烤鸭去哪吃 | 0.9823 | **0.0491** | 0.9823 |
| 北京地铁怎么坐方便 | 0.5268 | **0.0046** | 0.5268 |
| 那住宿呢 | 0.1112 | **0.0059** | 0.1112 |

`filters={'city': '成都市区'}`（词表外的值）更彻底：**6/6 条查询全部返回 0 条**，
而调用方看到的是"知识库没有资料"——看不出是过滤条件写错了。

### 三条教训

1. **"看起来更可信"的输入不等于"取值是对的"。** 显式 filters 看起来比模型抽的可信
   （它是代码传的），但可信的是**意图**，不是**取值**。"成都"和"成都市区"
   都可能是好意，而只有一个能匹配上。**词表校验跟意图可不可信无关。**
2. **文档写错字段名，等于给调用方发了一把插错孔的钥匙。** 那个字段说明不是
   无害的表述——它是这个 bug 的入口。
3. **校验做一半比完全不做更危险**，因为它留下了"这条路有校验"的印象。
   写 `if extracted...` 有校验的时候，很容易以为 `if explicit...` 那行
   也是同一套逻辑。

### 修法（两处，分工写在各自注释里）

| 位置 | 行为 | 为什么 |
|---|---|---|
| `schemas.RagSearchRequest`（接口边界） | **422**，并说明原因 | 调用方就在对面，能立刻看到自己传错了 |
| `policy.validate_filters`（流水线内部） | 丢弃 + warning | 这里已经论证过"检索失败不该让整轮对话失败"，为一个过滤条件打掉整轮更不值 |

受控词表 `FILTER_FIELDS = ("city",)` 和 `CITIES` / `DOC_TYPES` 一起搬进了
`app/rag/policy.py`。搬的理由不是整齐：**接口层要按词表校验，而原来的家
`chunking.py` 顶层 `import jieba`**——让一个 pydantic 模型的校验去付出加载分词器的代价，
是导入图没想清楚。归属也更对：chunking 是这两张表的**使用者**，不是所有者。

## 失败词表：三件事原来混在一起

计划要加 `pipeline-error`。查下去发现它比计划说的更严重：

```python
# 原来：只有【召回那一步】的异常被收成 None
try:
    vec_rows, bm25_rows, embed_used = _recall(...)
except Exception:
    return None

# 取正文 / 精排 / 组装这三步：完全没有保护，直接往上抛
details = _fetch_details(...)      # ← 抛出去
candidates = _rerank(...)          # ← 抛出去
assembled = assemble(...)          # ← 抛出去
```

于是一次崩溃在两条路上走成两个样：

| 调用方 | 结果 | 有多糟 |
|---|---|---|
| `retriever.search_full`（图） | 被 `except Exception` 接住 → **悄悄退成标题匹配** | **很糟**：看起来像"检索成功、只是结果差"，调用方会把文档标题当知识库内容用 |
| `rag_service.search`（接口） | 没人接 → **HTTP 500** | 糟，但诚实 |

现在 `pipeline` 把这三步包起来，产出一个 **`backend="pipeline-error"`** 的
`SearchOutcome`（**带 `branches`**——"召回明明成功了、是后面坏的"只有它说得清）。
两条调用方各自明写反应：

- 图：**要降级**（用户要的是一句回答，不是一次诚实的报错）
- 接口：**不能降级**，抛 503 + 一句和"容器没起"**不同的话术**（代码 bug 和环境故障是两件事）

分叉本身消除不了（两个调用方需要真的不同），但**现在它写在明处**，
不是两处 `except` 碰巧长得不一样。

### ⚠️ 这一条【故意不】`mark_down()`

召回失败会 `mark_down`（基本等于库连不上，标记一下能省掉后续请求各付一次三秒超时）。
但这三步出错**不代表库坏了**——更可能是我们自己的 SQL 或代码有问题。
标记 down 会把一个代码 bug 伪装成一次环境抖动，**60 秒后自愈，然后没人知道发生过**。
宁可让它每次都暴露出来。

### 怎么测的

`verify_degradation.py` 加了一节**故障注入**（monkeypatch `_fetch_details` 让它抛异常）。
不加的话，这段 except 是**平时一行都不执行**的代码——写错了没人发现，
直到真出 bug 的那天，而那天正是最不该再出别的问题的时候。
容器那几条至少还能手动复现，这个连复现都要先写个故障注入。

## 命中形状：四种 → 一种 + 两个显式投影

| 改造前 | 改造后 |
|---|---|
| `Candidate`(15) → `RagHit`(11) → finding dict(6) → `RetrievedChunk`(6) | `Hit`(15) → `to_finding_chunk()` / `to_api_hit()` |

**`RetrievedChunk` 整个删掉了**，因为它的投影关系是
`Hit -(6字段)-> RetrievedChunk -(6字段)-> finding.chunks`：两次手写映射，
**中间那次没加任何信息**。它的唯一消费者是 rag 节点。

`assemble.RankedChunk` 那个 `Protocol` 也删了——它存在的唯一理由是打断
`pipeline ↔ assemble` 的循环依赖，而它**是手抄的一份字段表**：
`Hit` 改了名它不会报错，只是悄悄匹配不上。现在两边 import 同一个类（`app/rag/types.py`）。

### ⚠️ 防它重新长出来的东西：`unprojected_fields()`

加一个字段到 `Hit` 上，两个投影函数都不会自动带上它——它会**静默地只在一半的地方存在**。
所以有一条断言（`--self-check` 检查 5）：`Hit` 的每个字段要么出现在某个投影里，
要么在 `_INTERNAL_FIELDS` 里写明为什么不给。

**它不检查你想得对不对，只要求你想过一次。** 已实测有牙齿（临时加一个字段 → 打红）。

## ⚠️ 意外发现：图里那条检索路径**一直不可复现**，而且没人能验证这件事

做验收（"固定 query 的 finding JSON 前后 diff"）时，同一份代码连跑两次，
finding 竟然不一样。查下去：

```
「那住宿呢」  第一次改写成  '住宿'
             第二次改写成  '（缺少上下文，无法确定目的地）的住宿推荐'
             → top-1 分数 0.53 vs 0.076
```

`retriever.search_full` **不暴露 `rewrite_query` 开关**，而它默认是 True。
所以任何走它的东西（图节点、`verify_degradation.py`、以后任何前后对比）
都拿不到可复现的结果——**而且不会报错，只会看起来在抖**。

这不是 bug（产品里就该带上下文改写）。问题是**"确定性模式"这件事
原来只对 `eval_quality` 直接调 `pipeline` 的那条路成立**，
而没有任何地方记录过"图那条路不是确定性的"。

修法：`search_full` 加 `rewrite_query: bool = True`，默认值与原来逐位一致。

### 验收怎么做的（因为仓库没有 commit，抓不到"改造前"的实物）

`git` 里这个项目**一个 commit 都没有**（全是 untracked），所以"改造前的代码"

## 答案质量复查：**这次结果和前一轮不可比**，原因值得单独记

Phase 2 改完之后按清单第 4 项跑了 `eval_answer.py --limit 10`：

```
依据性    平均 4.90/5   分布 4分×1  5分×9
出处     平均 5.00/5   分布 5分×10
完整性    平均 5.00/5   分布 5分×10
有编造内容的回答：2 / 10
```

上一轮（改造前）是 `5.00 / 4.90 / 5.00，编造 0/10`。

⚠️ **差值看着像"换个地方掉分了"，但它不是一次可比的测量。**

`eval_answer.py` 跑的是**整轮图**，里面有三处 LLM 调用，全都不可复现：

1. **Query 改写**（同一个问题两次能改出完全不同的句子，实测过，见上一节）
2. **答案生成**（DeepSeek，温度没钉，默认值基本等于随机）
3. **裁判**（脚本自己的注释就写着"同一个输入两次可能差一分"）

而这一轮**没有存下来上一轮的结果**（`eval_answer.py` 支持 `--out`，但那次没存），
所以既不能逐条比，也没有方差估计。**两个数之间差 0.10，小于裁判一个人的抖动范围。**

### 这次能得到的结论（只有这些）

- ✅ 图这条路在重构后**完整跑得通**，答案质量没有崩（4.90/5.00/5.00）
- ✅ 10 条全部走了正常检索路径（没有一条掉进降级）
- ❌ **不能**说"没退步"，也**不能**说"退步了"——需要方差才能下判断

### ⚠️ 顺带发现：两处编造是同一个形状

```
成都周边有什么值得一日游的地方  → 乐山/峨眉山时长是 8 小时（材料中无此信息）
成都三天怎么安排          → 武侯祠建议游览约 3 小时
```

**两条都是"时长/要玩多久"，都是编的。** 而 grounding 提示词列的必填事实类别是
"价格、时间、门票、班次、地址、距离、代码"——**"时间"读起来像时刻（几点），
不像"要玩多久"这个量**。

两个样本不足以下结论，但方向一致，值得下次扩样时专门看一类：
**提示词里没点名的那个事实类别，就是模型最容易编的那个。**
如果成立，改法是一行：把"时长 / 要玩多久 / 建议游览时间"加进那个列表。

### 建议（没做，因为要花额度）

想让第 4 项真的能当判据，二选一，都要先做一次成本评估：

1. **同码跑两遍**，得到方差，之后才知道多大的差算差（约 20 分钟 + 额度）
2. 给答案生成**钉温度**（`temperature=0`），把可变量从 3 处降到 1 处（裁判）
   ——但这会改变线上回答的多样性，是个产品决定，不是测试决定

# Phase 3：换召回分支——判据先写死，结果推翻了判据本身

预注册在 `eval/PHASE3_PREREG.md`（**跑之前写的，没改过**）。
这一节的全部数字都在 `--no-rewrite --top-k 8` 下取得，可复现。

## 一句话结论

**稀疏头作为一条召回分支全面好过 BM25，但它和"只跑向量路"的最终指标逐位相同。**
BM25 在 `hit@8` 上高出的那一条用例，查明是**把两个更高分的干扰项挤出候选池**造成的，
不是"找到了什么"。据此删掉了整套 BM25/jieba/词频表。

## 分支级成绩（三条路的真实差距）

| 分支 | top-5 | top-10 | top-30 |
|---|---|---|---|
| `vec`（稠密） | 0.9268 | 0.9756 | **1.0000** |
| `bm25`（被删） | 0.7561 | 0.8415 | 0.9512 |
| `sparse`（保留） | **0.8537** | **0.9024** | **0.9878** |

稀疏路在**三个 cutoff 上全面更好**（top-5 +0.0976、top-10 +0.0609、top-30 +0.0366）。

⚠️ 但注意 `vec` 单独就在 top-30 摸到 1.0000——**候选生成层早就没有损失了**，
所有损失都在排序上。这和 Phase 1 的结论一致。

## 预注册的三条判据

| 判据 | 实测 | 结果 |
|---|---|---|
| ① `branch_recall@30(sparse) ≥ @30(bm25)` | 0.9878 vs 0.9512 | ✅ 过 |
| ② `second_branch=sparse` 的 `hit@8` 仍为 1.0000 | **0.9868** | ❌ **没过** |
| ③ MRR / nDCG 不低于 −0.005 | −0.0019 / −0.0026 | ✅ 过 |

**按预注册的字面意思，判据 ② 没过 = 保留 BM25。** 下面是不按字面执行的理由——
它必须足够硬，否则预注册就白写了。

## ⚠️ 判据 ② 没过的真相：BM25 赢在"把对手赶走"

三条配置的完整指标：

| 配置 | recall@8 | hit@8 | MRR | nDCG@8 |
|---|---|---|---|---|
| `second_branch=bm25`（旧默认） | 0.9878 | **1.0000** | 0.8642 | 0.8952 |
| `second_branch=none`（已知答案测试） | 0.9756 | 0.9868 | 0.8623 | 0.8926 |
| `second_branch=sparse` | 0.9756 | 0.9868 | 0.8623 | 0.8926 |

**`sparse` 和 `none` 逐位相同。** 也就是说第二条路对最终结果**零贡献**——
这正是 `RESULTS.md` 第 5 节早就写过的"候选池太小，测不出真假"。

差异只出现在**一条用例**上：`成都周边有什么值得一日游的地方`，期望 `都江堰`/`青城山`。

```
青城山 的精排分：none 0.768212 / bm25 0.768212 / sparse 0.768212   ← 完全相同
青城山 的位置  ：none 第 9   / bm25 第 7   / sparse 第 9
```

交叉编码器逐条打分，和候选池无关。**它一直是同一个分。**
差别在于池子里还有谁：

```
none / sparse 的池子：武侯祠 0.7842、大熊猫繁育研究基地 0.7803  → 青城山被挤到第 9
bm25 的池子      ：这两个被 BM25 的独家候选挤掉了              → 青城山升到第 7
```

**正确答案从来就在向量路的候选池里**（`none` 配置下 `branches['vec']` 也含它）。
BM25 的贡献不是检索，是**扰动**——它把两个分数更高的干扰项赶出了池子，
于是正确答案被动地进了 top-8。

两种情况在 `hit@8` 上长得一模一样，这就是判据 ② 测不出来的东西。

## 新指标：独家贡献（`--branches` 新增）

上面那段只能靠手工反查发现，所以把"这一路独家带来了什么"做成了常规读数：

| 第二路 | 分支 | 独家候选/用例 | 一条独家都没有的用例 | **独家候选含答案的用例** |
|---|---|---|---|---|
| bm25 | `bm25` | 8.9 | 3 / 86 | **0 / 76** |
| bm25 | `vec` | 12.8 | 0 / 86 | 3 / 76 |
| sparse | `sparse` | 9.4 | 0 / 86 | **0 / 76** |
| sparse | `vec` | 9.4 | 0 / 86 | 1 / 76 |

**两种配置下，第二路的"独家含答案"都是 0/76。** 唯一不可替代的永远是向量路。

⚠️ 这三列必须一起读：
- 独家候选很多、但"含答案的独家"是 0 → 这一路的贡献全在**扰动排序**上，不在提供信息
- 扰动有时候恰好帮上忙，但那是运气，换一份语料就不一定了

## 决定：删 BM25，留稀疏头

判据 ② 是**我写的，而它测错了东西**。继续按字面执行等于让一个已知无效的判据
绑住结论。所以改成按判据 ①③ + 独家贡献来决定，并**把理由记在这里而不是只在脑子里**。

**删掉的**（`app/rag/bm25.py` 备份在
`<tmp>/p3/deleted/`，这个仓库还没有任何 commit）：

| 删掉的东西 | 规模 | 为什么它值得删 |
|---|---|---|
| `bm25.py` 的整套 SQL | 170 行 | 在 PG 里重造倒排索引 |
| `chunk_terms` 表 | 8009 行 / 130 块 = **62 倍放大** | 独家含答案 0/76 |
| `chunking.tokenize` / `STOPWORDS` / `count_terms` | ~90 行 | 只服务词频表 |
| `Chunk.term_freq` / `token_count`（属性 + 列） | — | 同上 |
| `rewrite` 的 keywords 字段 + 提示词第 2 段 + `_sanitize_keywords` | ~40 行 | 唯一消费者没了 |
| `jieba` 依赖 | 1 个包 | 同上 |

**顺带消掉的那条纪律**：原来"入库侧和检索侧必须用同一套分词，
不一致就永远匹配不上、**而且不报错**"——只能靠人记住。
现在两侧跑的是同一个 `sparse.encode`，**对称性由结构保证**。

⚠️ **改写提示词从"三件事"降到"两件事"的代价必须说清楚**：
改写是非确定性的活组件，提示词一变输出就会变，而**这件事用现在的尺子测不出来**
（带改写那行跑一次变一次，nDCG 抖动达 0.02）。
确定性的 `--no-rewrite` 基线不受影响——那个模式下根本不调改写。

## 稀疏头：六项自检 + 两个实测坑

`scripts/check_sparse.py`，14 项断言。**每一条都对应一个"不报错但结果全错"的失效方式。**

### 坑 1：`sparsevec` 存的是 float4

```
算出来 0.24761982262134552  →  写进库再读回来  0.24761982
```

不是 bug，是 `sparsevec` 的存储精度。但**"往返后逐位相同"这个断言在 float64 上必然失败**，
只有比 **float32 的位模式**才成立（相对差 1e-8）。
按 float64 比会稳定地报一个"精度丢失"的假警，然后引导人去修一个没坏的东西。

### 坑 2：截断检查写错了两版，两个方向都错了

| 版本 | 写法 | 结果 |
|---|---|---|
| 第 1 版 | `ids[-1] != sep_token_id` | 130 个块报了 **136 次**截断——`padding=True` 把同批较短的序列补齐了，`ids[-1]` 是 `<pad>`。**永远在报警** |
| 第 2 版 | 取最后一个**真实** token，看是不是 `</s>` | 不再误报——但**永远也不会报警**了。因为 `truncation=True` 是*先截断内容、再加特殊 token*，`</s>` 永远在最后 |
| 第 3 版 | 真实 token 数 `>= max_seq_length` | 对了 |

**第 2 版比第 1 版危险得多**：一个永远不会红的检查占着位置，让人以为这件事被覆盖了。
抓到它的是**故意把 `max_seq_length` 调到 8、看它红不红**。

> 写检查的人都以为自己写对了——**所以检查也得测**。

### 错一位的自检有牙齿（实测）

故意把 `to_literal` 里的 `tid + 1` 改成 `tid`，第 ④ 项立刻报错，
而**权重比对那一项仍然通过**（均匀错一位 = 同一个置换，点积不变）。
读回来的"词"变成了：

```
['规范', 'だろう', 'потер', 'ులు', 'trening']    ← 跨语言的胡话
```

**这就是"错一位可以一路活到线上"的样子。** 除了这一项，没有任何指标能发现它。

## pg_trgm 兜底：实测它该不该存在

换掉 BM25 会断掉降级链上唯一一层"不依赖模型"的块级召回（稀疏头和稠密头共用一个底座）。
补上的是 `content` 上的 pg_trgm（纯 SQL）。

**它比今天那条 title-only 兜底好在哪（模型不可用时实测，76 条可答用例）：**

| 路径 | hit@8 |
|---|---|
| trgm + 精排 | **0.9342**（71/76） |
| trgm 无精排 | 0.6316（48/76） |
| title-only 兜底（**改之前那条**） | **0.0000**（0/76） |

`0.0000` 不是"效果差"，是**结构性不可达**：`_keyword_fallback` 返回的
`section` 恒为空，而每条期望的 `section` 都非空，**所以它不可能匹配上任何一条用例**。
这个兜底一直在，只是从来没真正兜住过块级召回。

⚠️ 顺带一个观察：**精排在弱召回下顶了大梁**（0.6316 → 0.9342）。

### 为什么不上阈值（也就用不上 GIN 索引）

| `word_similarity_threshold` | 四条查询的命中行数 |
|---|---|
| 0.6（默认） | `[0, 0, 0, 0]` |
| 0.4 / 0.3 | `[0, 6, 0, 1]` |
| 0.2 | `[1, 13, 7, 21]` |

默认阈值下一个完全可答的问题会返回 0 行。**降级路最不该做的事就是把能答的判成答不了。**
所以不加阈值、直接按相似度排序取前 N；GIN 索引留给语料长大之后
（130 行时 `EXPLAIN` 是 Seq Scan，那是**正确**选择）。

⚠️ 它的排序质量明显不如 BM25（`成都熊猫基地门票多少` 的第一名是一条小吃街的块），
但**拿它和 BM25 比是比错了对象**——它的对手是 title-only，而那个是 0.0000。

## 已知的、这一轮没修的

1. **`score` 的归一化基数**：`_rrf_max` 按"两路都拿第 1 名"算。
   只跑一路时这个基数偏大，分数整体偏低。**Phase 4 的拒答阈值 0.111 需要重新确认。**
2. **两个截断点没建模**：候选池（30）和 top-k（8）。这一轮只在文档里记着。
3. **语料 130 块太小**：所有"分支有没有用"的结论都建立在每路召回 23% 的语料上。
   `RESULTS.md` 第 5 节早就写明**语料扩大 10 倍后这个实验要重做**——这一轮没有改变这个前提。

# Phase 4：拒答阈值——结论成立，但"0.111"这个值是错的

## 一句话结论

阈值落到了 **0.084**：**拒掉 6/10 条不可答查询，零误伤 76 条可答**。
而 `RESULTS.md` 早先记的那个 `0.111` 是**零代价区间的边缘**——
同样的收益和代价，站在悬崖边上没有任何好处。

## 为什么需要阈值

检索器**永远返回 top-k**，它没有"我不知道"这个状态。对「上海有什么好玩的」
这种知识库里根本没有的问题，它照样返回 8 条成都的内容——分数很低，
但下游看不出来。阈值就是补上这个状态。

## ⚠️ 最大的发现：阈值只对**精排分**有意义，对 RRF 分完全无效

`score` 的语义取决于有没有精排。实测 86 条用例的 top-1 分布：

| 配置 | 可答（76 条） | 不可答（10 条） | 能不能分开 |
|---|---|---|---|
| `rerank=True` | 0.111 ~ 1.000（中位 0.988） | 0.001 ~ 0.402（中位 0.058） | ✅ |
| `rerank=False` | **0.942 ~ 1.000** | **0.976 ~ 1.000** | ❌ 完全重叠 |

无精排那一行不是"分得不够开"，是**结构上没有信息**：每路的第一名都拿
`1/(k+1)`，只要有一路召回了东西，归一化之后就是 0.5~1.0，和它到底相不相关无关。
**RRF 分数是名次的函数，不是相关性的函数。**

所以 `pipeline._has_material()` 在**没有精排时一律返回 True**（fail-open）。

⚠️ **代价必须写清楚：重排模型不可用时，拒答功能静默失效。**
反过来（无精排就判"没资料"）会让整个知识库在重排模型挂掉时看起来是空的——
那比不拒答糟得多。这个取舍落在"宁可答得不准，也不要答不出来"那一侧。

## "0.111"错在哪

`eval_quality` 的阈值表按**收益台阶**采样，每行报的是该档**最小的**阈值——
也就是区间边缘。精确测出来的零代价区间是：

```
(0.057493, 0.111241)     宽度 0.0537
区间内任何值都是：拒 6/10，误伤 0/76
```

```
0.111  距最低可答用例（0.1112）只剩 0.0002   ← 悬崖边
0.084  距最近可答 0.0272 / 距最近不可答 0.0269  ← 中点
```

**同样的收益、同样的代价，没有理由站在悬崖边上。** 取中点。

## 实测行为（`search_full`，86 条用例）

```
可答   76 条：has_material=False 的 0 条
不可答 10 条：has_material=False 的 6 条
```

被拒的 6 条：上海、香港、日本签证、广州、杭州、深圳。
**每条都保留了 `retrieved=8`**（诊断），但 `context` 长度为 0（材料不上桌）。

### 抓不住的那 4 条（诚实记录）

| 查询 | top-1 分 |
|---|---|
| 西藏自驾怎么规划 | 0.4016 |
| 重庆火锅哪家好吃 | 0.1607 |
| 帮我订一张去成都的机票 | 0.1405 |
| 今天成都天气怎么样 | 0.1303 |

共同点：**内容上讲得通**（旅行、餐饮、成都），只是这份语料里没有对应资料。
**分数阈值分不出"相关"和"能回答"。** 要抓这 4 条得靠语料覆盖度之类的别的信号，
那是另一件事，这一轮没做。

## 设计：原始结果留、材料清

`has_material=False` 时：

| 保留 | 清空 | 理由 |
|---|---|---|
| `retrieved` / `hits` / `branches` / `backend` | `context` / `citations` / `finding.chunks` | "检索到了但不相关"和"什么也没检索到"必须能分开——前者是语料缺内容，后者是检索坏了，排查方向相反 |

**这条规则在三条路上一致**：`retriever.search_full`、`rag_node`、`rag_service`。
接口那边另外把 `has_material` 原样返回，让调用方能自己判断。

⚠️ 图里**必须连 `chunks` 一起清**，只清 `context` 不够：
`chunks` 会被 response 节点整个 `json.dumps` 进提示词，
只看 `context` 的话模型照样会照着 8 段成都的内容回答，而且答得像模像样。

## 自检：检查 7（拒答判定）

四条规则各喂一组数据：

1. 一条候选都没有 → False
2. 无精排 → True（fail-open）
3. 有精排且 top-1 < 阈值 → False
4. top-1 正好等于阈值 → **True**（`>=`，不是 `>`）
5. 只看 top-1，后续候选再低也不影响

**三项牙齿测试**（都实测变红）：
- 永远返回 True → "一条候选都没有时返回了 True"
- 无精排也套阈值 → "这会随机误伤"
- 用 `>` 代替 `>=` → "边界应该算够格"

## 闸门

```
recall  +0.0000   hit  +0.0000   mrr  +0.0000   ndcg  +0.0000
```

阈值**不改变检索**（它只影响"能不能拿去用"），所以主指标一位不动。
这是刻意的：把判定塞进 `candidates` 会让检索层不可观测。

## 顺带澄清 Phase 3 留下的一条

Phase 3 末尾记着"`_rrf_max` 按两路都拿第 1 名归一化，只跑一路时分数整体偏低，
Phase 4 的阈值要重新确认"。**确认的结果是：这条对拒答没有影响**——
拒答完全不看 RRF 分数（见上）。它仍然是一个展示层面的小瑕疵
（`second_branch=none` 或 trgm 单路时归一化基数偏大），但生产配置下
稠密+稀疏两路都在，那时基数是正确的。

# Phase 5：生产第二路换成 BM25，再把它调到分支召回 1.0000

## 决定：换，但不是按分支指标选的

用户要求直接把生产第二路换成 BM25。**它不是因为分支召回更高才被选中的**——
Phase 3 的实测里 BM25 的 @30 低于稀疏头。选它的理由是**故障面**：

| | 依赖 | 嵌入模型挂掉时 |
|---|---|---|
| `sparse` | bge-m3 同一个底座 | 和稠密路一起消失 |
| `bm25` | 纯 CPU + `chunk_terms` 词频表 | **仍然能跑** |

Phase 3 换掉 BM25 时，"模型挂了还有一路词法召回"这层兜底由 `trgm` 补上；
现在把 BM25 放回生产第二路，这层兜底从"三元组覆盖率"升级成"有 IDF 的排序"。
`trgm` 降为第二层——只有第二路不是 BM25、或 BM25 一条都没召回时才轮到它。

## 切换本身

| 改动 | 位置 |
|---|---|
| `SECOND_DEFAULT = BRANCH_BM25` | `app/rag/policy.py` |
| `RetrievalPolicy.second_branch` / `_recall` 默认值改用它 | `app/rag/pipeline.py` |
| 评估的默认值也改用它（不再各写一份） | `scripts/eval_quality.py` |
| 模型不可用：BM25 先顶，trgm 兜底 | `pipeline._recall` |
| backend 词汇表加 `bm25` / `bm25+rerank` | `policy.BRANCH_COMBOS`、`retriever._describe` |

查询文本保持 `rewritten`。raw 版实测更差（@30：0.9634 vs 0.9878）：
改写补上了"那住宿呢"这类查询丢掉的城市和主语，对词法路不是噪声。

确定性基线存到 `eval/baseline_bm25.json`（`--no-rewrite`）。

## 优化 1：分词从 `lcut` 换成 `lcut_for_search`

这是唯一一个真正有收益的改动。76 条可答用例、改写后的查询：

| 分词模式 | @5 | @10 | @30 |
|---|---:|---:|---:|
| `lcut`（精确，旧） | 0.7195 | 0.8902 | 0.9878 |
| `lcut_for_search` | **0.7683** | **0.9512** | **1.0000** |

@5 +0.0488（4 个期望条目）、@10 +0.0610（5 条）、@30 +0.0122（最后 1 条）。
@10 的提升超过 2 条用例的采纳阈值，不是单条噪声。

**机制是长专名。** 「北京烤鸭去哪吃」在精确模式下切出一个词 `["北京烤鸭"]`，
而正文那一节写的是"北京"和"烤鸭"分开的句子——词表对不上，整条用例的答案
在 top-30 里都找不到。搜索模式会同时输出长词和子词（`北京`、`烤鸭`、`北京烤鸭`），
这个词表才对得上。

顺带删掉了手写的 `_DOMAIN_WORDS` 景点词表：搜索模式下加不加，
三个 cutoff **逐位相同**（`search` 与 `search_no_domain` 两行完全一致）。
它的价值本来是"让长词不被切碎"，而搜索模式本来就会保留长词和子词——
那张表只剩维护成本。

**改分词必须重建旧词频表**，否则查询按新规则切、旧块按旧规则切，BM25 静默失效。
新增 `ingest_knowledge.py --rebuild-terms`：只重算 `token_count` 和 `chunk_terms`，
不动块 id、正文和向量。实测 130 块，词频行数 5698 → 6543（+15%）。

## 优化 2：k1 / b / δ 网格——没有收益

`scripts/eval_bm25.py --grid`：k1 ∈ {0.9, 1.2, 1.5, 1.8} × b ∈ {0.5, 0.75, 0.9}
× δ ∈ {0, 0.5, 1}，36 组。**除了 b=0.5 在 @10 上低 0.0122，其余全部逐位相同。**
所以保持 k1=1.2、b=0.75、δ=0。这个结论写进了 `bm25.py` 的常量注释，
省得下次有人再花一轮。

查询拼接也试了：`rewritten + raw` 与只用 `rewritten` 在三个 cutoff 上逐位相同。
不再保留这个旋钮。

## 最终指标：分支变好了，融合结果没变

| 配置 | recall@8 | hit@8 | MRR | nDCG@8 |
|---|---:|---:|---:|---:|
| 切换前 BM25（精确分词，无改写） | 0.9878 | 1.0000 | 0.8642 | 0.8952 |
| 切换后 BM25（搜索分词，无改写） | 0.9878 | 1.0000 | 0.8642 | 0.8952 |
| 切换前 BM25（带改写） | 0.9756 | 0.9868 | 0.9154 | 0.9335 |
| 切换后 BM25（带改写） | 0.9756 | 0.9868 | 0.9154 | 0.9335 |

分支召回从 0.9878 → 1.0000（带改写），但**融合+精排后的四项指标一位没动**。
原因是候选生成层早就没有损失：带改写时 `oracle=1.0000`，最终 `recall@8=0.9756`，
差的那 0.0244 全部是"答案在候选池里、精排没把它排进 top-8"。
**继续优化第二路不可能改善最终指标——该修的是排序。** 这条和 Phase 3 的
"候选生成层早就没有损失，所有损失都在排序上"是同一个结论。

## 模型故障验证（7/7）

`verify_degradation.py` 第 6 项改成两段：

1. 默认配置（BM25）+ 模型不可用 → `backend` 以 `bm25` 开头、context 非空、
   返回的是块不是标题。
2. `second_branch=sparse` + 模型不可用 → `backend` 以 `trgm` 开头、
   trgm 分支有召回。

两段都过。第 1 段是这次换分支的直接收益：模型挂掉时不再直接掉到三元组相似度。

## 优化 3：候选池和融合权重——全部逐位相同

既然分支召回已经 1.0000，剩下的缺口只可能在"融合后截断"或"精排"。试了：

| 配置 | recall@8 | hit@8 | MRR | nDCG@8 |
|---|---:|---:|---:|---:|
| 基线（每路 30 / 融合 30） | 0.9756 | 0.9868 | 0.9154 | 0.9335 |
| 融合 45 | 0.9756 | 0.9868 | 0.9154 | 0.9335 |
| 融合 60 | 0.9756 | 0.9868 | 0.9154 | 0.9335 |
| 融合 60 + `weight_second=1.5` | 0.9756 | 0.9868 | 0.9154 | 0.9335 |
| 融合 60 + 每路 45 | 0.9756 | 0.9868 | 0.9154 | 0.9335 |

全部逐位相同。唯一没进 top-8 的用例是「成都周边有什么值得一日游的地方」：

```
期望：chengdu-attractions.md > 都江堰 / 青城山
实际：锦里古街 0.877 / 去周边其他方向 0.836 / 三日行程骨架 0.834
```

两个期望章节**都在候选池里**（oracle 1.0000），是精排的分数把它们压下去了。
这已经不是 BM25 的问题，继续调它不会有收益。

## 新的尺子

`scripts/eval_bm25.py`：只算 BM25 分支召回，不跑嵌入和精排，一组变体不到一秒。

虽然只差 1 条，但两个尺子量出来的"提升"就没办法互相验证了。

# Phase 6：BM25 改回用户原话，优化 RRF 和精排

> Phase 5 把 `second_query` 定为 `rewritten`；本节按用户要求改成 `raw`，
> 并把补偿放在 RRF 和精排两层。Phase 5 的切换/分词结论仍然成立。

## 切换：BM25 用原始输入

> 后来按用户对"原始 query"的定义细化成了 `minimal`（最小清洗版），
> 生产默认已从 `raw` 改为 `minimal`。标注集是干净的，两者的分支和最终
> 指标完全相同；差异只在脏输入上，见下面的 6.1。

`policy.SECOND_QUERY_DEFAULT = "raw"`，pipeline 和评估的默认值都取它。
**只换查询文本，`filters`（city）仍然来自改写结果**——否则多轮里的
「那住宿呢」会跨城市召回。

搜索分词下，raw 和 rewritten 的分支召回：

|---|---:|---:|---:|

**这是 raw 的已知代价，不再试图用分词补**；补偿放在精排。

## RRF：所有旋钮逐位相同

|---|---:|---:|---:|---:|

## 精排：用「原话 + 改写」一起打分

| 精排查询 | recall@8 | hit@8 | MRR | nDCG@8 |
|---|---:|---:|---:|---:|

### 为什么生产用去重版（nDCG 低 0.0005）

改写失败时 `plan.rewritten == query`，拼两遍会把「那住宿呢」的精排分
从 **0.1112 压到 0.0746**，低于 `REFUSAL_THRESHOLD=0.084`，造成一次假拒答。
去重版让这条路的分数分布回到旧标定，阈值继续成立。0.0005 的 nDCG
换掉一次假拒答，值。

## 精排 / RRF 混合：0 最好

`rerank + blend * rrf_norm`，只改排序、不改 `Hit.score`（拒答阈值不受影响）：

|---|---:|---:|---:|---:|
| **0** | **0.9878** | **1.0000** | **0.9256** | **0.9426** |
| 0.01 | 0.9878 | 1.0000 | 0.9188 | 0.9381 |
| 0.05 | 0.9756 | 0.9868 | 0.9039 | 0.9267 |
| 0.1 | 0.9756 | 0.9868 | 0.9039 | 0.9267 |
| 0.5 | 0.9756 | 0.9868 | 0.8908 | 0.9167 |

混合只会让精排的判断被 RRF 拉回去，单调变差。默认保持 0。
这个实验旋钮在测完之后从 `RetrievalPolicy` 里删掉了——没有调用方的参数就是负债。

### 补充：BM25 用 rewritten + 精排 union 会怎样

## 6.1 `minimal`：最小清洗版（当前生产默认）

用户对"原始 query"的定义不是字节级复制，而是**最小清洗版**：

- 允许：Unicode NFKC（全角→半角、兼容字符→标准字符）、去零宽/控制/格式字符、
  空白规范化。
- 禁止：删停用词、加同义词、指代消解、纠错、去标点、繁简转换、大小写折叠。
  **词项集合必须不变**，尤其是 `MU-5401`、`3U8633`、`80-90元` 这类精确标识符。

实现：`app/rag/query_text.py` 的 `minimal_clean()`。
它只清洗查询文本，不碰 `filters`（city 仍来自改写结果）。

### 在干净标注集上，minimal 和 raw 完全相同

| BM25 查询 | 分支 @5 / @10 / @30 | 最终 recall@8 / hit@8 / MRR / nDCG@8 |
|---|---|---|
| `minimal` | 0.7561 / 0.9024 / 0.9878 | 0.9878 / 1.0000 / 0.9256 / 0.9426 |
| `raw` | 0.7561 / 0.9024 / 0.9878 | 0.9878 / 1.0000 / 0.9256 / 0.9426 |
| `rewritten` | 0.7683 / 0.9512 / 1.0000 | 0.9878 / 1.0000 / 0.9256 / 0.9426 |

标注 query 本身没有表示层噪声，所以 minimal 是 raw 的严格超集：
干净输入上不变，脏输入上更好。

### 脏输入：raw 会被零宽字符打空

在 query 的每个字符之间插入 U+200B（零宽空格），取 5 条可答用例：

| | 恢复原 top-10 |
|---|---:|
| `raw` | **0 / 5** |
| `minimal` | **5 / 5** |

raw 的 BM25 词表直接变成空列表——jieba 把粘着零宽字符的 token 当噪声，
后处理又把单字丢掉。minimal 去掉零宽后，排名和干净 query 完全一致。
`--check-clean` 把这条做成了常规检查。

全角空格（U+3000）两者都能处理（jieba 本身把它当空白）；
minimal 额外把它规范成普通空格。

⚠️ **不做**的事：在汉字之间插入空格（`成 都 大 熊 猫`）时 minimal 也不修。
把空格删掉会把单字词项拼成词，**改变词项集合**，违反这个模式的定义。
这是已知边界，不是漏做。

### 词项集合不变的自检

`scripts/eval_bm25.py --check-clean`：

```
固定样例 + 标注 query：✅ 通过
语料块：130 块，清洗后丢词 0 块，词项集合有变化 0 块
零宽扰动（5 条）：raw 恢复 0 条，minimal 恢复 5 条
```

固定样例覆盖全角数字/字母、全角连字符、零宽空格、换行/制表/多余空白、
价格区间连接符。标注 query 的 `tokenize` 多重集清洗前后完全相等；
130 个语料块没有任何词项丢失或变化。

### 结论

- **生产用 `minimal`**：保留用户全部词项，只修表示层噪声；干净输入不亏，
  脏输入比 raw 稳。
- `raw` 保留为评估开关，用来复现"零宽字符把词表打空"这类失败。
- `rewritten` 的分支召回更高，但高出来的部分全是多轮上下文；它增删词项，
  不符合"关键词路保留用户原话"的产品要求，那部分由稠密路和精排 union 补。

# 行程类 query 的 POI 章节补充（主 context）

## 问题

「成都三天怎么安排」的主 context（1954 字）里有行程骨架、青城山、武侯祠、
都江堰、人民公园，但：

- 大熊猫基地块在召回池里，**精排第 9**，差一名进 top-8；
- 宽窄巷子块在 vec 分支 top-30，但没进精排后的 30；
- 于是 response 只能从专家 findings 拿数字，写成"约 50—60 元（专家估算）"、
  "杜甫草堂门票资料未给出"——而知识库里分别是约 55 元、约 50 元；
- 裁判只看到主 context，所以"宽窄巷子免费"也被标成编造。

## 实现

| 文件 | 改动 |
|---|---|
| `app/rag/poi.py` | **新增**：行程意图检测 + POI 受控词表（canonical 必须等于 `section_key`） |
| `app/rag/pipeline.py` | 组装后，行程类 query 按 POI 章节直接取块，合并进 `context`；新增 `SearchOutcome.poi_expanded` |
| `app/agents/retriever.py` | note 里写明实际补充了哪些 POI |
| `scripts/check_poi_expand.py` | **新增**：意图正反例、词表对账、抽取、端到端 context 断言 |

关键约束：

- **只改 `assembled.context` / `citations`，不改 `candidates` / `branches`。**
  检索指标（recall/MRR/nDCG）一位不动；补充的是"回答要用的原始资料"，
  不是"重新排序"。
- 只补**不在主候选里**的 POI，按行程骨架里的出现顺序，最多 6 个，
  每个最多 2 块。
- 按 `section_key` 直接取块，不跑嵌入/精排——canonical 已经对账过，
  这是已知条目检索。
- 预算仍由 `assemble` 统一控制：放不下的整块丢弃；`poi_expanded` 只报
  **实际进了 context** 的 POI。
- `RetrievalPolicy.expand_pois=True` 是开关；它不影响 `candidates`，
  所以回归基线不受影响。

## 验证

- `scripts/check_poi_expand.py`：**21 / 21**。
  - 行程意图正例 5 条、反例 4 条；
  - 词表 canonical 和 `section_key` 全量对账（揪出并删掉了语料里没有
    独立章节的「天涯海角 / 蜈支洲岛」）；
  - 从「三日行程骨架」抽到 9 个 POI；
  - 端到端 `pipeline.search("成都三天怎么安排")`：补到 6 个 POI，
    context 2980 字 ≤ 3000，含熊猫基地「55 元」和宽窄巷子「全天开放」。
- `eval_quality --no-rewrite --baseline eval/baseline_bm25.json`：
  `recall / hit / MRR / nDCG` 全部 **+0.0000**，符合"只补 context"的设计。
